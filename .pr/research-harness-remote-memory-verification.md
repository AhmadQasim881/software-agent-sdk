### Actual memory retrieval

The owned fixture contained one file, `sample.py`, with `import json`. The local
operator service parsed that file without executing it, created an inventory
evidence record, and authored a decision referencing that evidence. A second
thread contained a matching `inventory` note to test recall scope.

Each request to `POST /api/mcp/test` started a real stdio MCP child through the
installed `openhands.research` module. The response advertised
`research_harness`; all five HTTP responses were 200, the outer `ok` was true,
the tool result's `is_error` was false, and the decoded tool payload's `ok` was
true. The recipe checked the complete returned record against the authored
record, beyond the connection status.

| Operation | Observation |
| --- | --- |
| `memory.get`, before restart | Recovered version 1, including exact text, source, tags, thread and evidence reference. |
| `memory.recall`, before restart | Returned only the selected thread's note; the other thread's matching note was absent. |
| `memory.get`, after restart | Recovered the locally updated version 2, preserving source, tags and evidence reference. |
| `memory.recall`, after restart | Returned the exact updated note, with the same thread restriction. |
| `memory.history`, after restart | Returned exactly versions 1 and 2, with `has_more: false`. |

The note was `memory_e659708480ad486fa7fdc0fd267149f7`, in thread
`thread_785e17baa3904f9598d70065f7554c43`, referencing
`evidence_11ce92aefeba49a6968689bd6d3a8162`. Version 1 said, “Read the saved
inventory before changing the sample.” Version 2 said, “Keep the saved inventory
and its source evidence together.” These were authored test decisions, not
automatically established findings.

Memory writes used the normal local operator service. The existing MCP test
endpoint documents that callers must choose a read-only tool call, so this
recipe used `memory.get`, `memory.recall` and `memory.history` there. These
operations preserve authored records, while the harness still records interface
audit events. No remote memory-write claim is based on this test endpoint.

After each response, the recipe checked descendants of the exact owned server
PID and found no remaining child with the tested `openhands.research` command
and state path. Every MCP connection was therefore closed at the observed
request boundary.

### Native SDK creation and reopening

Two separate client processes ran through `control-agent-server exec`, which
supplied the generated local server URL and key. The first used the public
`RemoteConversation` constructor with one configured tool:

```python
Tool(name=ResearchHarnessTool.name, params={"state_dir": str(state)})
```

It supplied no initial message and never called `send_message()` or `run()`.
Ambient project, user, public skills and SDK memory loading were disabled for
this isolated fixture. Closing the client with `delete_on_close=False` kept
the server conversation.

After an actual Agent Server restart, a second process used
`RemoteConversation.attach()` for the same UUID. Both processes received one
`ConversationStateUpdateEvent`, reported `idle`, and observed the exact native
tool name and state-directory parameter. REST readback preserved the complete
tool-module mapping, including
`research_harness -> openhands.tools.research_harness.definition`. The registry
also includes other registered modules; that is normal SDK serialization and
does not add them to the agent's configured tools.

Both clients observed empty model response, cost and token histories. The
conversation count changed `0 -> 1 -> 1 -> 0` across creation, reattachment and
explicit deletion. This verifies configuration and persisted registration
through native SDK/REST/WebSocket connection setup; it does not execute the
native tool executor inside a conversation.

## Product bugs, recipe changes and limitations

No product bug was established in this scoped pass. No existing server CLI
verb or feature-map entry changed. The new development recipe makes the
bounded memory workflow reproducible using the maintained launcher.

Two earlier fresh runs stopped at incorrect assertions in the new recipe:

| Attempt | Recipe correction | Cleanup |
| --- | --- | --- |
| `20261106-162337-ed99-research-memory`, under `/tmp/research-harness-remote-memory-o5177ztf` | `tools` contains strings, rather than objects with a `name` field. The actual first memory read had succeeded. | Verified port closure and private-state purge. |
| `20261106-162404-793f-research-memory`, under `/tmp/research-harness-remote-memory-5qeu40aw` | The persisted module map includes the client's registry. Assert the research mapping and persistence of the complete map, rather than an incorrectly assumed singleton map. MCP reads and SDK creation had succeeded. | Verified port closure and private-state purge. |

Their saved observations remain in their run directories. These were corrected
recipe assumptions, not product failures.

The native no-model execution boundary comes from
`openhands-sdk/openhands/sdk/conversation/impl/remote_conversation.py`:
`execute_tool()` explicitly raises `NotImplementedError`. The supported native
execution path is the normal server-side agent loop. That model-backed path,
live action/observation streaming, context compaction, interruption, external
hosts, containers and remote network deployment were outside this acceptance
check. A REST MCP pass must not be reported as a native agent-loop pass.

## Reproduce

From a repository checkout with its workspace dependencies installed:

```sh
.venv/bin/python -I .pr/research-harness-remote-memory-check.py
```

The recipe dynamically loads the existing verification CLI and calls its
normal `main(argv)` entry point for launch, doctor, HTTP, SDK subprocesses,
restart, evidence and cleanup. It keeps the whole lifecycle in one owning
process, creates fresh private directories and keys, and prints the resulting
evidence directory. No provider key is required. If a check fails, the `finally`
path still stops the owned server and writes the observations collected so far.

The repository's per-file pre-commit command was run for the added development
files. Its Python formatting/lint hooks exclude these report paths, so direct
`ruff format --check` and `ruff check` were also used for the recipe.
